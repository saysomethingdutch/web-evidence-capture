# 中国裁判文书网站点策略

本文件记录中国裁判文书网自然人姓名核查的站点专用策略。它是对 `SKILL.md` 通用规则的落地补充，不应机械套用到其他网站。

以下选择器和行为来自 2026 年 7 月的一轮实际批量核查。网站改版、浏览器升级或账号策略变化后，必须先做冒烟测试。

## 1. 查询口径

自然人司法核查采用“当事人”字段时，查询页面形态为：

```text
https://wenshu.court.gov.cn/website/wenshu/181217BMTKHNT2W0/index.html?pageId=<uuid>&s17=<姓名>
```

关键 DOM 约束：

```css
p[data-key="s17"][data-value="<姓名>"]
```

该元素应显示类似 `当事人：张三`。如果页面显示“全文：张三”、其他字段，或只在结果正文中出现“张三”，均不满足该检索口径。

## 2. 结果页验证

当前观察到的关键元素：

```text
结果总量：共检索到 X 篇文书
结果标题：a.caseName
页尺寸：select.pageSizeSelect
分页按钮：a.pageButton
```

每个站内结果页至少验证：

1. URL 仍属于裁判文书网结果入口；
2. 检索条件元素存在且字段和值正确；
3. 首页基准总量已读取；
4. 当前页标识符合预期；
5. 结果列表非空，或已进入明确的分页异常流程；
6. 首条结果标识相对上一页发生变化；
7. 页面未出现认证、验证码或风控信号。

非零结果只能分类为“同名结果待核阅”。仅凭姓名命中，不能把裁判文书归属于被核查自然人。

网站数据可能在同一天内更新，同一检索条件在不同时间显示的总量不一定完全一致。每份 PDF 所载查询时间和当时页面显示值是该次留痕的依据；重跑时如总量变化，应记录差异，不能为了与旧件一致而改写新页面。

## 3. 页尺寸

本轮实测中：

- 每页 5 条时，前三个站内结果页总体可稳定翻页和打印；
- 将页尺寸改为 10 或 15 条，首页可以显示，但部分后续页返回空列表或错误总量；
- 因此本轮最终采用每页 5 条。

这不是对网站的永久断言。后续项目如需调整页尺寸，应先用少量主体完成 P1 → P2 → P3 → PDF 的完整冒烟测试，并验证总量、页码和首条结果，不能只看下拉框是否接受该值。

## 4. 站内页码与 PDF 页码

裁判文书网结果分页属于 SPA 状态，地址栏不一定随 P1、P2、P3 改变。正式 PDF 建议：

- 页眉：查询时间、检索条件、每页条数、站内结果页码；
- 页脚：完整 URL 和 PDF 物理页码；
- 台账：分别记录 `site_page`、`page_size`、`pdf_physical_pages`。

不要用 PDF 的物理第 3 页代替“站内结果第 3 页”，也不要用相同 URL 推断两次打印来自同一站内页。

## 5. 中间空页

本轮观察到：首页总量非零时，P2 或 P3 偶发返回空列表，而重新发起查询后直接探测 P3 或 P4 又有结果；另有部分主体的 P3、P4 都为空。

标准处置：

1. 不将该主体或该页判为“无记录”；
2. 原样保存网站返回的空页，并在页眉标记 `分页异常：站内 Pn 返回空列表`；
3. 关闭或弃用当前可能已损坏的分页状态；
4. 从一次新的同字段查询出发，直接探测 Pn+1；
5. 将 Pn 空页与 Pn+1 相邻验证页一起放入异常材料组；
6. 写入异常台账，等待人工核阅。

重跑可以恢复一部分偶发空页，因此可对普通分页失败做有限重试；重试后仍为空时，必须忠实保留该状态，不能用其他页面覆盖。

## 6. 认证和风控

本轮出现过会话失效后另开 `noauth.html?v=1.1` 标签页，而原结果标签页仍可见的情况。脚本应在查询、翻页和打印前后扫描整个浏览器上下文。

建议纳入整批停止词：

```text
noauth
验证码
访问过于频繁
访问受限
账号封禁
```

普通网络或导航错误可按主体有限重试，例如最多 3 次；出现登录失效、验证码、访问限制或封禁时，必须停止整批并保留断点，由人工处理后再恢复。不得以切换账号、绕过验证等方式规避站点控制。

访问间隔、批次大小和批间休息应做成显式配置。一次未触发限制的高速运行不能推导出安全速率。

## 7. 多页原子提交

同一主体的 P1–P3，或异常主体的 P1–P4，应视为一个证据组：

```text
pending/<subject_id>/P01.pdf
pending/<subject_id>/P02.pdf
pending/<subject_id>/P03.pdf
pending/<subject_id>/P04.pdf  # 仅异常探测时
```

推荐流程：

1. 全部页面先写入 `pending/<subject_id>/`；
2. 验证字段、姓名、基准总量、站内页码、页面状态、URL 页脚、物理页数和哈希；
3. 全组通过后，原子安装到正式目录并写入完成台账；
4. 任一页失败时，整组留在隔离区并写入异常台账；
5. 恢复运行只认台账状态，不以正式目录中存在部分文件判断完成。

## 8. 手工补页的归档检查

手工下载文件即使命名为“姓名page3.pdf”，仍须从 PDF 内容重新确认：

- 检索条件确为 `当事人：姓名`；
- 文件内容属于该主体而非上一位或下一位；
- 结果总量和站内页码合理；
- 页眉、完整 URL 页脚、版式方向和物理页数符合当前模板；
- 文件哈希已记录。

本轮曾出现“文件名是 A，PDF 内检索条件却是 B”以及“姓名相同但实际使用全文检索”的手工件。清单驱动归档只能防止移动错位，不能替代内容级核验。

## 9. 运行前冒烟测试

浏览器、Playwright 或站点版本发生变化时，先用一个非敏感样本验证：

1. 专用 Chrome 实例和 CDP 连接正常；
2. 登录态可用，且上下文没有 `noauth` 标签；
3. “当事人”条件可被 DOM 明确读取；
4. P1、P2、P3 的当前页和首条结果正确变化；
5. PDF 为约定的 A4 纵向版式，页眉页脚完整；
6. 台账能同时记录站内页码与物理页数；
7. 暂停、异常停止和断点恢复路径均可用。

只有冒烟测试通过，才进入批量阶段。
